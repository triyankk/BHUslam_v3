# QR-triggered VIO performance testing

Software/startup validation and remaining physical checks are recorded in
[the validation report](../reports/vio-benchmark-validation.md).

This workflow measures Gemini/ORB-SLAM3 on the Jetson without transmitting
navigation data to the Cube or running the ToF bridge. The capture, QR decoder,
resource sampler and report generator are C++17. Shell scripts provide entry
points; the browser draws the interactive 3D plot. No Python was introduced.

## Organized entry points

| Location | Purpose |
|---|---|
| `bin/vio-test` | User-facing commands for this workflow |
| `bin/bhu` | Unified dispatcher for existing camera, replay, Cube and ToF tools |
| `build/main/bin/` | Compiled binaries; never copy them into system directories |
| `configs/vio-benchmark.yaml` | Camera/IMU settings; explicit `loopClosing: 1` |
| `assets/test_vio.png`, `.svg` | Exact QR payload, generated by native `vio_qr` |
| `runs/vio/<UTC timestamp>/` | One invocation's results, settings, metrics and plots |
| `deploy/systemd/bhu-vio-test.service` | Optional user service; one test per start |
| `deploy/udev/99-bhu-gemini.rules` | Optional persistent camera permission rule |

The older system `vio-flight.service` belongs to another checkout under
`/home/atas/vscode/intellisense_slam`, launches Python and was inactive when
inspected. It is not used, renamed or overwritten. The launcher refuses to run
if that service is active. Existing recorder/replayer and ToF tools retain their
paths; this workflow centralizes the VIO test without moving dependencies or
deleting historical data.

## Build and prepare

```bash
bash scripts/bootstrap.sh       # includes native ZBar/QRencode development files
bash scripts/build.sh
bin/vio-test qr
bin/vio-test power-info
```

Print `assets/test_vio.svg` at roughly 12–16 cm square on matte white paper,
with its white border intact. Show it to the left IR camera from a distance at
which it occupies a useful part of the frame. Phone displays can have poor IR
contrast, so a printed carbon-black QR is preferred. Real-camera QR recognition
still needs a user-presented test; software fixtures exercise decoding first.

Camera permissions must survive reconnects for unattended arming. The existing
temporary `setfacl` grant expires when unplugged. To install the narrow device
rule, an administrator can run:

```bash
sudo install -m 0644 deploy/udev/99-bhu-gemini.rules /etc/udev/rules.d/
sudo udevadm control --reload-rules
# Reconnect the camera so the rule is applied. The user must belong to plugdev.
```

## 15 W and comparison runs

This Jetson's local `/etc/nvpmodel.conf` defines mode 0 as `15W`, mode 1 as
`25W` and mode 2 as `MAXN_SUPER`. The initial query returned `MAXN_SUPER`.
The workflow does not silently switch modes, lock clocks, or reboot the machine.
To select the intended battery profile before a test:

```bash
bin/vio-test power-15w           # sudo may request your password
bin/vio-test arm
```

`power-15w` discovers the mode by name in the local configuration rather than
assuming another Jetson's mode numbering. Respect any reboot request from
`nvpmodel`. `arm` defaults to requiring the actual `15W` profile and refuses
to label a MAXN run as 15 W. An explicitly labelled comparison can use:

```bash
bin/vio-test arm --power-profile MAXN_SUPER
```

That command requires MAXN_SUPER to already be selected; it does not change
power mode. Repeat the same route, camera settings, lighting and starting
temperature for each profile, preferably several times. Browsers and background
work contribute to module power; keep their use consistent, and close the live
viewer for headless power measurements when possible. The saved report remains
available after the test. Actual 15 W performance is not established by MAXN
or fixture tests.

NVP mode is a module power policy, not a 15 W limit on the complete battery
system. The resource log samples the INA3221 `VDD_IN` module rail using voltage
times current. It does not measure complete carrier/camera/regulator/battery
consumption. Missing rail access is reported as unavailable. Profile names and
CPU clock limits/governor are recorded, and start/end profile differences flag
an inconsistent run.

## Start, run and stop

1. Run `bin/vio-test arm` and wait for **ARMED**. Vocabulary loading completes
   before arming, so its startup cost is excluded from the test interval.
2. Present the QR whose decoded payload is exactly `test_vio`. Two detections
   at the native 2 Hz scan cadence start the test. Case and extra spaces differ.
3. Remove the QR. Translate smoothly in several directions and add gentle
   rotations during initialization. Keep the scene textured and well lit.
4. Continue a route that returns to the starting area and revisits the same
   scene from a similar viewpoint. Allow enough duration and motion for inertial
   initialization/refinement; a 2–3 minute loop is a useful initial protocol.
5. Present `test_vio` again to stop. It must have been continuously absent for
   at least 2 seconds, and the run must be at least 5 seconds old. Keeping the
   start QR visible cannot toggle immediately back to stop.
6. Wait for finalization and the printed report path. Capture stops first;
   queued loop work gets a short drain interval, and shutdown waits for mapping,
   loop correction and global bundle adjustment before trajectory export.

The default maximum run duration and QR-wait timeout are each 600 seconds.
Override with `--seconds` and `--idle-seconds` (each at most 3600). Limits and
SIGINT are recorded as distinct stop reasons, rather than claiming a QR stop.
Each arming invocation runs one test, then exits; arm again for the next test.

The standalone benchmark drives no GPIO. The separate headless
[Cube integration workflow](cube-vio-test.md) uses the Cube's MAVLink buzzer
for ready/start/stop, VIO publication status, report completion and errors.
Use `bin/vio-test cube-arm` for that explicit navigation-enabled bench mode;
ordinary `bin/vio-test arm` retains its no-navigation behavior.

## Plots and measurements

During a test, open **http://127.0.0.1:8766** on the Jetson. Drag the 3D graph to
rotate and use the wheel to zoom. For another computer:

```bash
ssh -L 8766:127.0.0.1:8766 atas@JETSON_IP
```

Then open that same localhost URL. The server is loopback-only. It stops when
the test application exits; use the saved standalone report afterward.

Each run includes:

- `report.html`: interactive standalone 3D plot for the complete test interval,
  metrics, and optional final-map view. It needs no CDN or internet connection.
- `trajectory.png`: native-generated static 3D projection, with start/end marks.
- `plot_data.json`: the plot data and metadata embedded in the HTML report.
- `frames.csv`, `tracking.csv`: per-frame time, tracking and IMU initialization,
  poses, segment identity, QR overhead and frame/track processing time.
- `metrics.json`: processing FPS; tracking/capture-age P50/P95/P99; first IMU
  initialization, initialization counts, reset and confirmed-loop counts.
- `resources.csv`: approximately 1 Hz process CPU usage, memory, CPU frequency,
  rail input power and maximum available thermal-zone temperature. CPU frequency
  is sampled from CPU0. CPU percent
  uses 100% per core; memory includes the loaded vocabulary.
- `loop-events.csv`: only applied ORB loop graph corrections, when any occur.
- `trajectory_optimized.txt`, `keyframes_optimized.txt`: final-map exports if
  a usable map survives. They can cover a subset of the full test.
- `run.json`, settings copies, `binary.sha256`, `console.log`, `events.jsonl`.

Plot green segments represent tracking with initialized IMU; amber represents
visual tracking before initialization. Lost tracking, initialization transitions
and map-correction segments are not connected as one continuous route. The
online path precedes final optimization; final-map coordinates are shown
separately because they may use a different origin. No poses are fabricated
across reset gaps. A run without initialized VIO must not be presented as a
successful VIO result just because some visual poses exist.

Loop closure is enabled, not guaranteed. An upstream patch records an event
only after loop graph correction and loop-edge insertion. Rejected candidates,
relocalizations and generic `MapChanged()` notifications do not count as a
closed loop. The QR is a trigger, not a loop-closure marker or ground truth.
Returning to a QR does not establish exactly the same physical camera pose.

Track-call timing excludes QR/remap overhead; `frame_wall_ms` includes their
iteration cost and any IMU wait. Effective processing FPS and overwritten video
counts expose inability to keep up with 30 FPS. The newest-frame policy drops
pending video frames rather than accumulating stale work, while retaining IMU
history. Estimated capture age still uses the provisional delivery-based clock
mapping. Sampled rail energy includes only its logged coverage window, not
an invented battery-energy measurement for unsampled intervals.

The prior VIO runs reset repeatedly. This workflow measures that behavior; it
does not establish calibrated VIO accuracy or a flight-ready external nav source.

## Optional service

The unit is a user service, running under the same camera-access permissions:

```bash
mkdir -p ~/.config/systemd/user
cp deploy/systemd/bhu-vio-test.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user start bhu-vio-test.service
journalctl --user -u bhu-vio-test.service -f
```

Do not run the foreground launcher simultaneously. The service defaults to 15 W,
does not change power mode, and does not restart or auto-rearm after a test.
`systemctl --user stop bhu-vio-test.service` sends SIGINT and permits cleanup
and report generation. The unit is provided but not enabled at boot by this work.

## Rebuild a report and validate software

```bash
bin/vio-test report runs/vio/RUN_DIRECTORY
ctest --test-dir build/main --output-on-failure
```

Native fixtures cover exact/rotated QR decoding, payload rejection, debounce,
minimum run duration, continuous visibility, report calculations and accepted
versus rejected loop evidence. Loopback/PTY tests in the broader suite require
host socket permission. Camera-presented QR start/stop, a real loop correction,
and measured 15 W runtime performance require a physical test.

and the pinned local ORB-SLAM3 `System.cc` / `LoopClosing.cc` implementation.
